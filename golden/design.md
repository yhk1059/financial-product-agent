# 골든 데이터셋 설계 (v1 확정)

## 1. 목적과 범위
- **목적:** 증권사 PB·상담 직원용 금융상품 질의응답 에이전트의 성능을 재고, 개선 효과를 비교할 기준점을 만듭니다. 에이전트의 목표는 "정형 금융상품 데이터를 스스로 탐색·연산하고 근거에 기반해 답변"하는 것입니다.
- **대상 사용자:** PB·상담 직원입니다. 질문은 업무 말투로 쓰고, 상품명·코드·수치가 답변에 들어가야 합니다.
- **데이터 범위:** PostgreSQL public 스키마의 5개 테이블입니다. 모든 정답은 이 테이블에 대한 SQL로 계산할 수 있어야 합니다.

  | 테이블 | 내용 |
  |---|---|
  | `pref01n001` | 국내 상장 ETF·ETN |
  | `pref02n001` | 해외(미국) 상장 ETF·ETN |
  | `prfd01n001` | 펀드 (클래스 단위 행) |
  | `prbd01n001` | 채권 (판매 단위 LOT·시장별 행) |
  | `domestic_etf_holdings` | 국내 ETF 구성종목 |

- **데이터 기준일:** 2026-08-21 스냅샷입니다.
- **참고하지 않는 것:** 외부 지식(기업 지배구조, 시장 뉴스 등), DB의 `ontology`·`semantic` 스키마, 다른 폴더의 기존 골든 데이터셋.

## 2. 해석 정책
문항은 `policy_refs`로 아래 정책 ID를 참조합니다. 정답은 이 정책을 따른 해석으로 계산합니다.

| ID | 정책 |
|---|---|
| **P-SCOPE** | 질문에 판매 여부가 없으면 **전체 데이터**를 대상으로 합니다. 판매 조건은 질문에 "판매중·판매 가능·매수 가능"이 있을 때만 적용합니다. |
| **P-SALE** | "판매중/판매 가능"의 테이블별 정의입니다. 국내 ETF·ETN: `pd_sale_yn='1'`. 해외 ETF·ETN: `pd_sale_yn='1'`. 펀드: `sale_yn='판매중'`. 채권: `buyable_quantity > 0`(매수가능수량이 있는 LOT, v2·G1 결정). v1은 `trade_price IS NOT NULL`(판매 물량 등록)이었으나 그중 절반 이상이 수량 0이라 바꿨습니다. |
| **P-UNIT** | 개수의 단위입니다. 채권은 종목 기준(`COUNT(DISTINCT pd_no)`)으로 셉니다. 같은 종목이 장내·장외와 LOT별로 여러 행이기 때문입니다. 단, **판매 가능(매수 가능 수량이 있는) 채권의 개수는 판매 건(행) 기준(`COUNT(*)`)**으로 셉니다(C1-01 결정). 펀드는 클래스 행 기준이 기본이고, "대표펀드 기준"이라고 하면 `rptt_ksd_itm_no` 기준으로 셉니다. 구성종목 관련 ETF 수는 `COUNT(DISTINCT item_id)`로 셉니다. |
| **P-PRODUCT** | "ETF"라고 하면 `pd_grp_no='ETF'`, "ETN"이라고 하면 `'ETN'`만 셉니다. "상장상품"이나 "ETP"라고 하면 둘 다 셉니다. |
| **P-NULL** | 조건·정렬에 쓰는 컬럼이 NULL인 행은 제외합니다. 결측이 많은 컬럼(10% 이상)을 쓴 경우, 답변에 제외 사실을 밝혀야 합니다. |
| **P-ZERO** | 보수율 0의 처리입니다. 해외 ETF(`pref02n001.cu_charge_rt`)의 0은 **실제 값으로 포함**합니다(C1-05·C2-04 결정). 국내 ETF(`pref01n001.cu_charge_rt`)의 '0'은 미입력으로 보고 제외합니다. |
| **P-TIE** | Top-N 경계에 동률이 있으면, 동률 항목은 어느 것을 골라도 정답입니다(`accept_alternatives`). |
| **P-GRADE** | 신용등급 순서는 AAA > AA+ > AA0 > AA- > A+ > A0 > A- > BBB+ > BBB0 > BBB- > BB0 > BB- > B+ > B- > C0 입니다. "AA- 이상"은 목록으로 비교합니다. |
| **P-NAME** | 상품·종목명은 정확히 일치하는 것을 기본으로 매칭합니다. 국내 ETF 상품명은 `pd_abrv_nm`(예: 'KODEX 200')을 씁니다. 표기 변형이 있으면 문항 `notes`에 적습니다. |
| **P-DATE** | 만기·기간 계산의 기준일은 오늘이 아니라 데이터 기준일 2026-08-21입니다. "N년 이내"는 `mat_dt <= DATE '2026-08-21' + INTERVAL 'N years'`로 계산합니다. |
| **P-UNITS** | 수익률·보수율·변동성·금리는 % 단위 숫자입니다(1.5 = 1.5%). 금액(순자산, AUM, 발행금액)은 원 단위이고, 답변에서는 억원·조원 환산을 허용합니다. 단, 해외 상장상품(`pref02n001`)의 금액(일간 순자산총액·거래대금)은 USD입니다(2026-10-18 결정). |
| **P-ASSET** | 자산군 키워드를 컬럼에 대응시킵니다. 국내 ETF "채권형/주식형"은 `wu_inv_ast_type`(채권/주식…)으로, 해외 ETF는 `wu_inv_ast_type`(Bond/Equity…)으로 봅니다. 펀드 "주식형/채권형"은 제로인 대유형 `zrin_btyp_nm`으로 봅니다. 채권 "원화채권"은 `curr_cd='KRW'`입니다. |
| **P-CASH** | 구성종목 집계에서 현금성 항목('원화예금', '설정현금액', '원화현금', '현금성자산', '100%현금설정액')은 제외합니다. |
| **P-OUTLIER** | 이상치로 보이는 값도 원본 그대로 사용합니다(C3-04 결정). 답변에서 이상치 가능성을 언급하는 것은 허용합니다. |
| **P-OOS** | 5개 테이블로 답할 수 없는 질문(기업 지배구조, 편입 비중, 없는 컬럼, 미래 예측)에는 "데이터에 근거가 없다"고 답해야 정답입니다. 추측으로 답하면 오답입니다. |

## 3. 질문 분류
| 분류 | 정의 | v1 문항 수 |
|---|---|---|
| **C1 조건 탐색** | 조건 2개 이상으로 상품 목록·개수를 뽑습니다. 등급·만기·지역·자산군·판매 여부 등을 조합합니다. | 7 |
| **C2 연산·집계** | 개수, 평균, 합계, 그룹별 집계, 비율을 DB에서 계산합니다. | 7 |
| **C3 순위** | Top-N과 최댓값·최솟값을 구합니다. 결측이 많은 컬럼으로 정렬하는 경우도 포함합니다. | 5 |
| **C4 관계 탐색** | 테이블 안의 관계를 1~2단계 따라갑니다. 종목 → 편입 ETF, ETF → 구성종목, 펀드 클래스 → 대표펀드, 발행기관 → 채권, 기초지수 → 국내·해외 ETF. | 6 |
| **C5 비교** | 그룹 간·테이블 간 수치를 비교합니다. | 2 |
| **C6 범위 밖** | 데이터로 답할 수 없는 질문입니다. 근거가 없다고 답하는지 봅니다. | 3 |

- **커버리지 기준:** 테이블마다 최소 4문항을 둡니다.
- **난이도:**
  - `easy`: 단일 테이블, 조건 1~2개
  - `medium`: 조건 3개 이상, 집계, 결측 처리
  - `hard`: 조인, 2단계 관계, 정책을 여러 개 적용

## 4. 문항 형식 (`questions_v2.yaml`)
| 필드 | 필수 | 내용 |
|---|---|---|
| `id` | ✅ | `C{분류}-{번호}` (예: `C1-01`) |
| `category` | ✅ | `C1`~`C6` |
| `difficulty` | ✅ | `easy` / `medium` / `hard` |
| `tables` | ✅ | 정답 계산에 쓰는 테이블 |
| `question` | ✅ | PB 말투의 질문 |
| `interpretation` | ✅ | 정책을 적용한 해석을 한 문장으로 |
| `policy_refs` | ✅ | 적용한 정책 ID 목록 |
| `answer_type` | ✅ | `count` / `scalar` / `list` / `table` / `refusal` |
| `gold_sql` | C6 외 ✅ | 정답 SQL. `sql_guard`를 통과해야 합니다. |
| `key_columns` | C6 외 ✅ | 결과 비교에 쓸 컬럼 |
| `order_matters` | | 순서까지 맞아야 하면 `true` (Top-N 순위) |
| `must_mention` | | 답변에 꼭 나와야 할 것: 기준일, 적용 필터, 결측 제외 등 |
| `decision_needed` | | 해석이 갈리는 지점. `options`마다 `label`과 `sql`이 있고, 검증 스크립트가 선택지별 결과를 기록합니다. |
| `notes` | | 데이터 특이사항, 설계 의도 |
| `gold_result` | (자동) | 검증 스크립트가 `golden/gold_results_{버전}.json`에 기록하는 정답 스냅샷. YAML을 손으로 고치기 쉽도록 별도 파일에 둔다. |
| `accept_alternatives` | (수동) | 동률 등으로 허용할 다른 답. `- {rank: 3, key: 'TIGER ...'}`처럼 순위(1부터)와 키 값을 적습니다. `verify_golden.py`의 `tie_candidate` 경고를 보고 추가합니다. |
| `key_alternatives` | | 키 컬럼마다 같은 상품을 가리키는 다른 식별 컬럼(예: `{pd_abrv_nm: [pd_nm, pd_itm_no]}`). 정답 SQL이 이 컬럼들도 조회해야 합니다. 실행 정확도와 답변 정확도 모두 어느 식별자로든 같은 상품이면 맞은 것으로 봅니다(S4). |
| `label_columns` | | `key_columns` 중 정답 SQL이 지어낸 라벨 컬럼(예: C5-01 `market`의 'domestic'). 값 대신 일대일 대응으로 비교하고, 답변 정확도 검사에서 뺍니다. |
| `mention_keywords` | `must_mention` 있으면 ✅ (5.6) | `must_mention`과 같은 순서의 키워드 목록. `'표현1\|표현2'`는 동의 표현 |
| `forbidden_patterns` | C6 ✅ (5.6) | 답변에 나오면 오답인 정규식 목록 |

## 5. 채점 설계 (2026-10-17 확정·구현)
### 5.1 원칙
- **규칙 기반으로 채점합니다.** 채점에는 LLM을 쓰지 않습니다. 그래야 결과를 재현할 수 있고, HCX 분당 한도(60회·6만 토큰)를 에이전트 실행에만 쓸 수 있습니다. LLM 판정은 규칙으로 판정할 수 없는 항목이 쌓였을 때 별도 축으로 추가합니다.
- **실행과 채점을 분리합니다.** 실행 결과(답변, 실행 SQL, 조회 행)는 JSONL로 저장합니다. 채점 규칙이 바뀌면 에이전트를 다시 돌리지 않고 저장된 파일로 다시 채점합니다(`--rescore`).
- **답변 문자열보다 SQL 결과를 먼저 봅니다.** 이전 평가 스크립트(`run_eval.py`)는 정답 값이 답변에 들어 있는지만 확인했습니다. 그래서 우연히 일치하거나 숫자 하나만 맞아도 통과합니다. 여기서는 실행 정확도를 주 지표로 삼고, 답변 텍스트 검사는 보조 축으로 둡니다.
- 참고: ady95/ontology-tutorial `common/evaluate.py`에서 실행 틀(JSONL 저장, 재채점, 구성 비교, N회 안정성 표, 비용 기록)과 `'표현1|표현2'` 동의어 표기, 금지 표현 검사를 가져옵니다. 답변 문자열 포함 여부로만 채점하는 방식은 가져오지 않습니다.

| `src/portfolio_agent/golden_eval.py` | 순수 채점 함수(결과 비교, 숫자 정규화, 키워드 판정)입니다. DB와 LLM 없이 단위 테스트할 수 있어야 합니다. |

### 5.3 실행 기록 (`AskTrace`)
`ask()`는 그래프 스트림에서 아래 값을 모읍니다.

| 필드 | 내용 |
|---|---|
| `answer` | `generate_query`가 마지막으로 낸 도구 호출 없는 응답 |
| `selected_tables` | `select_tables` 결과 |
| `queries` | 실행한 `run_query` 호출 목록. 항목마다 `sql`(검토 후 최종 인자), `ok`(결과가 `Error:`로 시작하지 않음), `output`(도구 반환 텍스트) |
| `gave_up` | `max_query_attempts`를 넘겨 포기 모드로 답했는지 |
| `llm_calls` | LLM 호출 수. LLM을 부르는 노드(`select_tables`, `generate_query` 등)의 실행 횟수로 셉니다. |
| `tokens` | 응답의 `usage_metadata`가 있으면 입력·출력 토큰 합계, 없으면 `null` |
| `seconds` | 질문 하나의 경과 시간. 429 재시도 대기가 포함되므로 `retry_wait_seconds`를 따로 기록합니다(`invoke_with_retry`에 누적 카운터 추가). |

### 5.4 결과 비교 (실행 정확도, C1~C5)
1. **비교 대상 쿼리:** 성공한 쿼리 중 **마지막 쿼리**를 먼저 보고, 맞지 않으면 **앞선 성공 쿼리**를 뒤에서부터 봅니다(S2, `exec_match: "earlier"`). 답변을 낸 뒤 확인 쿼리를 더 돌린 경우를 오답으로 만들지 않기 위해서입니다. 답변 정확도가 함께 필요하므로 탐색 쿼리의 우연 일치는 걸러집니다. 채점기는 그 SQL을 `sql_guard.validate`에 다시 통과시키고 `db.fetch`로 다시 실행해 전체 결과(최대 200행)를 얻습니다. 에이전트가 본 결과는 50행·8,000자로 잘려 있기 때문입니다. 다시 실행한 행은 JSONL에 저장해서 재채점 때 DB 없이 씁니다.
2. **컬럼 대응:** 에이전트의 컬럼 별칭은 정답과 다르므로 이름이 아니라 **값으로 대응**시킵니다. `key_columns`의 각 정답 컬럼에 대해, 값 목록이 정규화 후 일치하는 에이전트 컬럼을 찾습니다. 여러 개를 대응시켜야 하면(`table`) 가능한 조합을 모두 시도합니다. 정답 키 컬럼은 최대 2개이므로 조합 수는 작습니다. 에이전트 결과에 여분의 컬럼이 있는 것은 허용합니다.
3. **유형별 판정:**

   | `answer_type` | 판정 |
   |---|---|
   | `count`, `scalar` | 에이전트 결과가 1행이고, 그 행의 어떤 셀이 정답 값과 일치하면 정답입니다. 여러 행이면 오답입니다. |
   | `list` (`order_matters` 없음) | 키 값의 **집합**이 같아야 합니다. 빠진 것이나 남는 것이 있으면 오답입니다. |
   | `list` (`order_matters`) | 에이전트 결과의 **앞 N행**(N = 정답 행 수)의 키 순서가 같아야 합니다. 에이전트가 N보다 많이 조회하고 답변에서 N개만 고른 경우도 허용합니다. `accept_alternatives`의 대체 행은 같은 순위 자리에 허용합니다(P-TIE). |
   | `table` | 키 컬럼 튜플의 **다중집합**이 같아야 합니다. 그룹 순서는 보지 않습니다. `label_columns`는 값이 달라도 정답 라벨과 일대일로 대응하면 맞은 것으로 봅니다. |

4. **숫자 정규화:** `Decimal`, `float`, 숫자 문자열은 float로 바꿉니다. 아래 중 하나를 만족하면 같은 값으로 봅니다.
   - 둘 다 소수점 둘째 자리로 반올림한 값이 같다.
   - 에이전트 값의 소수 자릿수가 d(1 이상)이면, 정답을 d자리로 반올림한 값과 같다. 예: 정답 0.5103, 에이전트가 `ROUND(...,2)`로 0.51을 낸 경우.
   - 정수 개수는 정확히 일치해야 한다.

   비율은 `scalar`에 한해 ×100 또는 ÷100 변형도 허용하고 `scale_variant: true`로 표시합니다(예: C2-06에서 55.9 대신 0.559).
5. **여러 쿼리로 나눠 푼 경우 (`table`만):** C5처럼 그룹을 쿼리 두 개로 나눠 조회할 수 있습니다. 마지막 쿼리가 맞지 않으면, 결과 행이 모두 정답 행(라벨 컬럼 제외)에 들어맞는 쿼리들을 모읍니다. 그 쿼리들이 정답 행을 빠짐없이 덮으면 `exec_match: "union"`으로 정답 처리하고 요약표에 따로 보여 줍니다. 정답에 없는 행을 낸 쿼리(탐색용 조회 등)는 합집합에 넣지 않습니다.
6. **결과 표시:** `exec_match`는 `last`, `earlier`, `union`, `none`, `no_query` 중 하나입니다.
7. **대체 식별 컬럼 (S4):** `key_alternatives`가 있으면 키 컬럼을 대체 컬럼으로 바꾼 조합마다 비교해 하나라도 맞으면 정답입니다. 예: C3-01은 약어명(`pd_abrv_nm`), 정식명(`pd_nm`), 상품코드(`pd_itm_no`) 중 어느 것으로 답해도 됩니다.

### 5.5 답변 정확도와 충실도
- **답변 정확도 (`answer_ok`, C1~C5):** 정답의 핵심 값이 답변 텍스트에 있는지 봅니다. 대상은 `count`·`scalar`의 값, `list`·`table`의 키 값(10개 이하일 때)입니다. 매칭은 숫자 변형(이전 `run_eval.py`의 `_variants`를 `golden_eval.py`로 옮김)(콤마, 반올림, `:.1f`·`:.2f`)을 쓰고 공백은 무시합니다. 금액은 억원·조원 환산도 허용합니다(P-UNITS). 값이 10개를 넘는 목록은 이 축에서 제외합니다(`answer_ok: null`). `key_alternatives`가 있으면 대체 식별 값(정식명·코드) 중 하나만 나와도 그 값은 충족합니다.
- **답변 충실도 (`grounded`, 전체):** 답변에서 숫자를 모두 뽑아 각각 성공한 쿼리의 `output`에 있는지 봅니다. 연도·날짜·기준일(2026, 08, 21), 질문에 나온 숫자, 순위 번호(1~N)는 제외합니다. 근거 없는 숫자는 `ungrounded_numbers`로 기록합니다. 이 축은 오탐이 있을 수 있어 처음에는 **정답 판정에 넣지 않고 참고 지표로만** 씁니다.

- **컬럼 진단 (`columns_missing`·`columns_extra`, C1~C5):** 정답 SQL과 에이전트의 마지막 성공 쿼리를 sqlglot으로 파싱해, 참조한 컬럼 이름을 비교합니다. 스키마 카드(`data/schema_catalog.json`)에 있는 실제 컬럼만 남기므로 별칭·CTE 컬럼은 빠집니다. 테이블 구분 없이 컬럼 이름만 비교합니다. 정렬·출력용 컬럼도 섞이고 같은 답을 다른 컬럼으로 낼 수 있으므로, **정답 판정에는 쓰지 않고** `wrong_result`의 원인을 좁히는 진단으로만 씁니다. 핵심 컬럼을 문항에 직접 적는 방식(`required_columns`)은 기준선에서 컬럼 실수가 반복되는 문항에만 나중에 검토합니다.

### 5.6 필수 언급과 거절
- 현재 `must_mention`은 "판매 건 기준 개수" 같은 설명문이라 키워드로 판정할 수 없습니다. 그래서 문항에 **`mention_keywords`** 필드를 추가합니다. `must_mention`과 같은 순서의 목록이고, 항목마다 `'표현1|표현2'`처럼 동의 표현을 나열합니다. 하나라도 있으면 그 항목을 충족합니다.

  예 (C1-01): `mention_keywords: ["판매 가능|당사 판매|판매 물량", "판매 건|건 기준|건수"]`
- **필수 언급 키워드는 질문에 없는 표현만 씁니다 (S1).** 질문에 이미 있는 표현은 답변이 질문을 따라 말하기만 해도 통과하기 때문입니다. `tests/test_golden_schema.py`가 이를 검사합니다. 질문이 이미 정한 단위(예: "클래스는 몇 개야?")를 되풀이하는 필수 언급은 두지 않습니다.
- **거절 정확도 (C6, S3):** 일반 거절 표현만으로는 통과하지 못합니다. 문항마다 **거절 이유 키워드**를 따로 요구합니다. 예: C6-01 '자회사 정보·지배구조', C6-02 '비중 정보·데이터·컬럼', C6-03 '예측·추천 불가'. 여기에 **`forbidden_patterns`**(정규식)를 둡니다. 하나라도 걸리면 오답입니다.
  - C6-01: `에코프로비엠|에코프로에이치엔|에코프로머티` (기억에 의존한 자회사 추측)
  - C6-02: `\d+(\.\d+)?\s*%` (비중 수치를 지어낸 경우), `삼성전자 … 정보가 없`·`KODEX 200 … 찾을 수 없` (사실이 아닌 거절 이유. v1 기준선이 이 이유로 통과했었다)
  - C6-03: 특정 ETF를 추천하는 표현. 상품명 목록 대신 `추천드립니다|사세요|매수하시` 같은 표현으로 잡습니다.

  C6에서 쿼리를 실행한 것 자체는 감점하지 않습니다. 편입 여부를 확인하는 것은 정당한 탐색이기 때문입니다.
- 금지 표현은 공백을 유지한 채 비교합니다("불가능"이 공백 제거 후 다른 표현에 걸리는 오판을 막기 위해서입니다).

### 5.7 문항 판정과 실패 원인
- **문항 정답 (`correct`):**
  - C1~C5: `exec_match ≠ none` **이고** `answer_ok ≠ false` **이고** 필수 언급을 모두 충족
  - C6: 거절 키워드를 충족 **하고** 금지 패턴이 없음
- **세부 점수:** 축마다 따로 남겨서 어디가 약한지 보이게 합니다. 요약표 열은 실행 정확도, 답변 정확도, 필수 언급, 거절, 충실도 참고입니다.
- **실패 원인 (`fail_reason`):** 오답 하나에 첫 번째로 해당하는 원인을 자동으로 붙입니다.

  | 코드 | 조건 |
  |---|---|
  | `error` | 실행 중 예외 |
  | `table_miss` | `selected_tables`에 문항의 `tables`가 빠짐 |
  | `no_query` | C1~C5인데 성공한 쿼리가 없음(SQL 오류 반복, 포기 모드 포함) |
  | `wrong_result` | 쿼리는 성공했지만 결과가 정답과 다름 |
  | `answer_mismatch` | 결과는 맞지만 답변에 값이 틀리거나 빠짐 |
  | `missing_mention` | 필수 언급 누락 |
  | `refusal_fail` | C6에서 거절하지 않았거나 금지 패턴이 걸림 |

### 5.8 일관성과 비용
- `--runs N`(기본 1)이면 같은 구성을 N번 실행해 `{label}_r{i}.jsonl`로 저장합니다. 문항별 정답 횟수를 `3/3`(안정 정답), `0/3`(안정 오답), 그 사이(불안정)로 집계합니다. 일관성 지표는 "안정 정답 수"와 "불안정 문항 수"입니다.
- 비용은 문항별로 `seconds`, `retry_wait_seconds`, `llm_calls`, `query_attempts`, `tokens`를 기록하고 구성 단위로 합계와 중앙값을 냅니다.
- **한도 계산:** 30문항 × 문항당 LLM 3~5회 = 90~150회입니다. 분당 60회 한도에서 한 번 돌리는 데 최소 2~3분 이상 걸립니다. 문항 사이에 고정 대기는 두지 않고 `invoke_with_retry`에 맡깁니다.

- **요약 (`data/golden_runs/{label}_summary.md`):** 전체 정답률, 축별 정답률, 분류(C1~C6)·난이도별 정답률, 실패 원인 분포, 비용 합계
- `gold_results_v2.json`에 문항이 없거나, 문항의 `sql_sha`(정답 SQL 해시, `verify_golden.py`가 기록)가 현재 `gold_sql`과 다르면 실행 전에 중단하고 `verify_golden.py` 실행을 안내합니다.

  - 정답: `uv run python scripts/verify_golden.py --questions golden/holdout_v2.yaml --out golden/gold_results_holdout_v2.json`. 측정: `uv run python scripts/eval_golden.py --set holdout --label <커밋>_<모드>_holdout`.

  - `glossary.yaml`: 질문 표현 → 정본(개념·속성·값 집합), 동의 표현과 혼동어
  - `rules.yaml`: 조건·시점·예외·계산 규칙
  - `review_log.yaml`: 사람의 결정과 이유, 근거 자료 충돌, 데이터 확인 기록, 검토 승인 내역
  - 추출 과정은 `analysis/extraction_worksheet.md`에 있습니다. 정의는 문항 전용이 아니라 일반 개념으로 쓰고, 문항 id는 추적용 `motivated_by`에만 둡니다. 정답 SQL은 옮겨 적지 않습니다.
  - `tests/test_ontology.py`가 구조·실재성(`schema_catalog.json`)·누수(문항 id, 골든 고유명사, 정답 SQL 술어 중복)·커버리지(골든 30문항)를 검사합니다.
